# Анализ производительности и отчет о нагрузочном тестировании

Настоящий документ содержит детальный анализ результатов нагрузочного тестирования API информационной системы **«АРМ Замдекана: модуль элективных курсов»**, проведенного с использованием фреймворка **Locust** в 4 последовательных сценариях с непрерывным профилированием системных ресурсов (CPU, RAM).

## 2. Сравнительный анализ сценариев: 50 пользователей против 100 пользователей

Сравнение поведения системы при увеличении числа одновременных пользователей с 50 до 100 наглядно демонстрирует переход через предел насыщения архитектуры:

1. **Пропускная способность (RPS):**
   - При **50 пользователях** система достигает пиковой производительности: **73.0 RPS** и обслуживает **13 002 запроса** за 3 минуты. Сервер стабильно справляется с потоком обращений.
   - При **100 пользователях** пропускная способность катастрофически деградирует до **3.2 RPS** (падение более чем в 22 раза!), за 3 минуты сервер успел обработать всего **488 запросов**.

2. **Задержка (Latency / Response Time):**
   - При **50 пользователях** среднее время отклика составляет **370.7 мс**, что находится в допустимых пределах для интерактивных пользовательских интерфейсов.
   - При **100 пользователях** среднее время отклика подскакивает до **29.97 секунд** (рост более чем в 80 раз!), а максимальное время ожидания достигает **90.15 секунд**, приводя к массовым сетевым тайм-аутам клиентов.

3. **Надежность и уровень ошибок (Error Rate):**
   - При **50 пользователях** уровень ошибок равен **0.00%** (ни одного сбоя из 13 002 запросов).
   - При **100 пользователях** доля ошибок подскакивает до **25.00%** (`ConnectionResetError`, `ReadTimeoutError`, `HTTP 500 / 504`). Клиенты начинают отваливаться по таймауту сокета.

4. **Потребление ресурсов (RAM / Memory Footprint):**
   - При росте очереди клиентов объем потребляемой оперативной памяти монотонно увеличивается с **89.0 МБ** (50 польз.) до **107.4–111.4 МБ** (100 польз.) из-за буферизации незавершенных соединений и накопления объектов контекста запросов в памяти Uvicorn.

## 3. Выявленные узкие места (Bottlenecks)

1. **Блокировки дисковой файловой СУБД SQLite:**
   - SQLite ориентирована на однопользовательский или слабонагруженный сценарий и использует файловые блокировки (`table/database-level locking`) при операциях записи (`POST /courses`, `PATCH /courses/{id}`, `PATCH /students/{id}`). При 100 параллельных клиентах конкурирующие транзакции выстраиваются в очередь ожидания освобождения файла БД (`database is locked`), что парализует параллельные чтения.
2. **Синхронный драйвер базы данных в асинхронном Event Loop:**
   - Эндпоинты FastAPI вызывают синхронные методы `session.exec()`, `session.commit()` и `session.refresh()` через стандартный движок SQLAlchemy без `AsyncSession`. На время выполнения блокирующих дисковых I/O-операций основной поток Python asyncio Event Loop замораживается, препятствуя приему новых входящих TCP-соединений.
3. **Одиночный рабочий процесс Uvicorn (Single Worker):**
   - Бэкенд запущен в режиме одного процесса (`1 worker`). Из-за глобальной блокировки интерпретатора (GIL) в CPython сервер ограничен вычислительной мощностью одного ядра процессора, создавая эффект "бутылочного горлышка" при разборе HTTP-заголовков и валидации схем Pydantic.
4. **Отсутствие индексов и полнотекстового поиска:**
   - Поиск по названию курса (`/courses?search=...`) выполняется с помощью оператора `col(Course.title).icontains(...)`, что при отсутствии индексов приводит к полному сканированию таблицы (`Full Table Scan`).

## 4. Рекомендованные способы оптимизации

Для обеспечения стабильной работы при нагрузке 100+ одновременных пользователей рекомендуются следующие архитектурные оптимизации:

### Способ 1. Миграция на промышленную клиент-серверную СУБД с асинхронным драйвером
- **Решение:** Заменить встраиваемую SQLite на **PostgreSQL** (версии 16+) с использованием пула соединений и полностью асинхронного драйвера `asyncpg` + `ext.asyncio` в SQLAlchemy / SQLModel:
  ```python
  from sqlmodel.ext.asyncio.session import AsyncSession
  from sqlalchemy.ext.asyncio import create_async_engine
  engine = create_async_engine("postgresql+asyncpg://user:pass@db:5432/electives", pool_size=20, max_overflow=10)
  ```
- **Эффект:** Устранение файловых блокировок, поддержка версионирования строк (MVCC) для неблокирующего параллельного чтения/записи, разгрузка Event Loop.

### Способ 2. Горизонтальное масштабирование воркеров Uvicorn / Gunicorn
- **Решение:** Запуск Uvicorn с несколькими рабочими процессами по числу доступных ядер CPU (`workers = 2 * CPU_CORES + 1`):
  ```bash
  uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
  ```
  В продакшн-контуре: использование reverse proxy (Nginx / Traefik) для терминирования SSL, распределения трафика (round-robin) и отдачи статики.
- **Эффект:** Параллельная утилизация всех ядер процессора, отсутствие задержек на этапе TLS-handshake и разбора HTTP-пакетов.

### Способ 3. Внедрение слоя кэширования для Read-Heavy эндпоинтов (Redis / InMemory)
- **Решение:** Эндпоинты каталога элективов `GET /courses` и списка заявок `GET /applications` запрашиваются значительно чаще, чем происходят мутации. Интеграция **Redis** с TTL 15–30 секунд:
  ```python
  # псевдокод
  @router.get("/courses")
  async def get_courses(search: str | None = None):
      cache_key = f"courses:{search}"
      if cached := await redis.get(cache_key):
          return json.loads(cached)
      courses = await fetch_courses(search)
      await redis.setex(cache_key, 30, json.dumps(courses))
      return courses
  ```
  С инвалидацией кэша при операциях `POST /courses`, `PATCH /courses/{id}`, `DELETE /courses/{id}`.
- **Эффект:** Снижение обращений к базе данных на 80-90%, гарантированный отклик эндпоинта чтения за < 5 мс при 100+ пользователях.

### Способ 4. Добавление B-tree индексов в структуру реляционных моделей
- **Решение:** Добавить индексы в `app/models.py`:
  - `Course.title`: для быстрого поиска по подстроке/префиксу (`index=True`).
  - `Application.course_id` и `Application.student_id`: внешние ключи с индексами для ускорения `JOIN` и фильтрации.
  - `Application.status`: индекс для фильтрации заявок по статусу.
- **Эффект:** Снижение алгоритмической сложности запросов фильтрации с $O(N)$ до $O(\log N)$.
